# O02-SG001은 무엇이고, 무엇을 승인해야 하는가

## 결론부터 말하면

`O01`은 이미 **어떤 검색 lane을 실행해야 하는지, 실행했는지, 결과가 없었는지, 일부만 끝났는지**를 정확히 기록하도록 완성됐습니다. 하지만 다음 단계인 `O02`에는 **검색 backend가 반환한 한 건의 결과를 어떤 구조로 저장하고, 관계 방향을 어떻게 판정하며, 여러 검색 결과를 어떤 순서로 합치고, 어느 성능부터 PASS로 볼지**가 아직 제품 계약으로 정해져 있지 않습니다.

이 상태에서 구현을 시작하면 개발자가 임의로 다음을 결정하게 됩니다.

- 검색 후보의 ID와 hash에 무엇을 포함할지
- 같은 문서를 중복으로 볼지 하나로 합칠지
- `A가 B를 증가시킨다`와 `B가 A를 증가시킨다`를 어떻게 구분할지
- lexical, semantic, citation, graph 결과를 어떤 규칙으로 합칠지
- vector 검색 결과만 있어도 성공으로 볼지
- backend 중단·오래된 index·잘못된 응답을 실패, 차단, 부분 성공 중 무엇으로 볼지
- Recall과 nDCG가 어느 정도여야 검색 품질을 통과시킬지

이 결정들은 단순 구현 세부사항이 아닙니다. 검색 결과가 이후 Evidence Pack, Parliament, validation과 promotion에 들어갈 수 있는지를 좌우하는 **제품·과학적 의미 결정**입니다. 그래서 `O02-0001`은 코드를 쓰지 않고 `O02-SG001`로 fail-closed 중단했습니다.

이 문서의 아래쪽에는 그대로 검토하고 승인할 수 있는 권장 HumanDecision 전문을 넣었습니다. **이 파일은 이해와 승인을 위한 초안이며, 파일이 존재하는 것만으로 제품 결정이 승인되거나 RAH blocker가 해제되지는 않습니다.**

## 쉬운 비유

O01과 O02를 도서관 검색에 비유하면 다음과 같습니다.

- `O01`은 사서에게 “제목 검색, 의미 검색, 인용 검색, 반대 결과 검색, null 결과 검색을 모두 하라”는 검색 계획과 체크리스트를 줍니다.
- `O02`는 각 검색 시스템에서 나온 책과 논문을 실제 후보 카드로 만들고 순위를 매깁니다.

현재 O01 체크리스트는 완성됐지만 O02 후보 카드 양식과 채점표가 없습니다.

예를 들어 같은 논문이 제목 검색에서는 1위, 의미 검색에서는 4위, 인용 검색에서는 2위로 나왔다고 가정하겠습니다. 지금 계약만으로는 다음 질문에 답할 수 없습니다.

1. 이것을 후보 3개로 저장할지 후보 1개로 합칠지
2. 합친다면 어느 점수를 사용할지
3. 어느 검색 방식에서 발견됐는지 모두 보존할지
4. 오래된 index에서 나온 결과를 허용할지
5. 원문 위치가 없는 결과도 evidence 후보로 볼지
6. 반대 방향 관계를 지지 결과로 잘못 섞지 않는지

채점표 없이 구현하면 테스트도 정답을 가질 수 없습니다. 이것이 `O02-SG001`입니다.

## 정확히 무엇이 비어 있는가

### 1. 검색 후보의 canonical 구조

현재 `SearchLaneReceipt`에는 최종 `result_ids`와 개수가 있지만, 그 ID가 가리키는 개별 후보의 구조가 없습니다.

최소한 다음을 고정해야 합니다.

- 후보 ID와 content hash 규칙
- QueryPlan, lane, query와의 연결
- corpus snapshot과 index version
- backend 및 adapter version
- 원본 backend request/response hash
- source/document/artifact locator
- 원본 rank와 channel별 score/rank
- relation direction 판정
- scope estimate
- 중복 병합 이력
- 검색 설명과 ranking feature
- full text/source span 확인 여부

### 2. backend에 전달할 입력

lexical, semantic, citation, relation backend가 서로 다른 임의 입력을 받으면 replay와 provider 교체가 불가능합니다. provider-neutral request에 무엇이 봉인되는지 정해야 합니다.

### 3. lane과 QueryPlan query family의 연결

QueryPlan에는 다음 배열이 있습니다.

- `forward_queries`
- `reverse_queries`
- `null_queries`
- `boundary_queries`
- `method_queries`
- `novelty_queries`

그러나 11개 lane 각각이 어떤 배열을 소비하는지 고정돼 있지 않습니다.

### 4. 관계 방향

현재 다음을 구분할 closed vocabulary와 exact answer가 없습니다.

- 같은 방향
- 주어와 목적어가 뒤집힌 방향
- inverse predicate로 같은 사실을 표현한 경우
- 양방향 관계
- 방향이 없는 대칭 관계
- 판정 불가능

### 5. ranking, deduplication과 cutoff

다음 순서가 바뀌면 결과가 달라집니다.

- 무결성 검사
- 중복 병합
- channel 내부 순위 정규화
- 여러 channel fusion
- feature 계산
- cutoff
- 동점 처리

현재는 그 순서와 상수가 없습니다.

### 6. snapshot과 stale-result 처리

QueryPlan을 만든 뒤 corpus나 index가 바뀌었을 때 예전 결과를 성공으로 받아도 되는지 정해져 있지 않습니다. 이 값은 재현성과 evidence provenance에 직접 영향을 줍니다.

### 7. 실패와 fallback

backend가 없거나 잘못된 JSON을 주거나 일부 query만 처리했을 때 `BLOCKED`, `FAILED`, `PARTIAL` 중 어느 상태인지, 다른 channel로 조용히 대체해도 되는지가 비어 있습니다.

### 8. “vector-only retrieval avoided”의 실행 규칙

현재 manifest에는 문장만 있고 검사식이 없습니다. semantic vector 결과만 downstream에 전달해도 되는지 판정할 수 없습니다.

### 9. 두 required check의 정답

O02의 required check는 다음 두 개지만 fixture와 threshold가 없습니다.

- `retrieval_benchmark`
- `relation_direction_test`

### 10. O01과 O02의 소유 경계

현재 workflow에서 O02 lane node는 generic `ResultEnvelope`를 내고, O01 planning executor가 `SearchLaneReceipt`를 봉인합니다. O02가 SearchLaneReceipt까지 만들지, 후보만 만들지 명시해야 합니다.

### 11. 해결 작업의 exact write scope

현재 O02 write scope는 `python/epistemic_foundry/retrieval/lanes/**`뿐입니다. canonical schema, test, fixture, benchmark와 workflow를 쓸 권한이 없습니다.

### 결정 B — 후보 ID와 content hash를 분리합니다

후보의 안정된 정체성과 결과 내용의 무결성을 혼동하지 않습니다.

`candidate_id`는 다음 identity preimage의 JCS-equivalent canonical JSON SHA-256으로 계산합니다.

```text
plan_hash
+ lane
+ query_hash
+ canonical_source_key
+ source_version
+ source_snapshot_hash
```

형식:

```text
RC-<64 lowercase hex>
```

`candidate_hash`는 모든 resolved provenance, backend observation, rank, score, feature와 duplicate lineage를 포함한 전체 후보 content preimage의 SHA-256입니다.

형식:

```text
sha256:<64 lowercase hex>
```

`candidate_id`, `candidate_hash`, 생성 시각과 storage locator는 self/volatile field이므로 candidate content preimage에서 제외합니다.

한 lane이 여러 query를 사용하므로 `query_batch`는 다음 구조를 canonical family order로 정렬한 객체입니다.

```json
{
  "lane": "counterevidence",
  "families": [
    {"family": "FORWARD", "queries": ["..."]},
    {"family": "REVERSE", "queries": ["..."]}

```

`SearchLaneReceipt.query_text`에는 이 객체의 JCS-equivalent canonical JSON 문자열을 저장하고, `query_hash`에는 그 UTF-8 bytes의 SHA-256을 저장합니다. 따라서 한 lane에 query가 여러 개여도 하나의 lane receipt와 정확히 결박됩니다.

backend raw response는 신뢰하지 않습니다. O02 adapter가 schema, snapshot, index, rank와 locator를 검증한 뒤에만 RetrievalCandidate로 정규화합니다.

### 결정 E — 11개 lane의 query-family mapping을 고정합니다

| lane | 필수 query family | 추가 규칙 |
|---|---|---|
| `lexical` | `FORWARD` | exact term, identifier, phrase를 보존 |
| `semantic` | `FORWARD` | vector result임을 provenance에 명시 |
| `citation` | `FORWARD` | query를 citation seed로 사용 |
| `entity_variable` | `FORWARD` | entity, variable, unit edge로 확장 가능 |
| `mechanism` | `FORWARD` | mechanism edge와 intermediate node 보존 |
| `counterevidence` | `FORWARD`, `REVERSE` | reverse가 필수이고 forward는 비교 context로 사용 |
| `null` | `NULL` | null/no-effect/equivalence family만 사용 |
| `boundary` | `BOUNDARY` | moderator, threshold, neighboring scope 사용 |
| `method` | `METHOD` | measurement/design/construct family 사용 |
| `temporal` | `FORWARD` | policy의 date/version/correction filter 필수 |
| `external_novelty` | `NOVELTY` | corpus-external scope와 stop rule 필수 |

선택된 lane의 필수 family가 비어 있으면 backend를 임의 호출하지 않고 `INVALID_QUERY_FAMILY_BINDING`으로 fail closed합니다.

### 결정 F — 관계 방향 vocabulary를 고정합니다

```text
SAME_DIRECTION
REVERSE_DIRECTION
INVERSE_PREDICATE
BIDIRECTIONAL
NO_DIRECTION
UNRESOLVED
```

의미는 다음과 같습니다.

| 값 | 의미 |
|---|---|
| `SAME_DIRECTION` | source의 subject, predicate, object가 canonical relation과 같은 방향 |
| `REVERSE_DIRECTION` | 같은 predicate에서 subject와 object가 뒤집힘 |
| `INVERSE_PREDICATE` | 등록된 inverse predicate와 뒤집힌 인자를 사용해 같은 canonical fact를 표현 |
| `BIDIRECTIONAL` | source가 양쪽 방향을 명시적으로 주장 |
| `NO_DIRECTION` | symmetric/non-directional relation이라 방향 비교가 적용되지 않음 |
| `UNRESOLVED` | predicate mapping, argument order 또는 source grounding이 부족해 판정 불가 |

예를 들어 canonical relation이 `A parent_of B`일 때 exact answer는 다음과 같습니다.

| source relation | expected |
|---|---|
| `A parent_of B` | `SAME_DIRECTION` |
| `B parent_of A` | `REVERSE_DIRECTION` |
| `B child_of A` | `INVERSE_PREDICATE` |
| `A parent_of B`와 `B parent_of A`를 모두 주장 | `BIDIRECTIONAL` |
| `A correlated_with B` | `NO_DIRECTION` |
| predicate 또는 argument grounding 불충분 | `UNRESOLVED` |

`UNRESOLVED`와 `NO_DIRECTION`을 direction match로 취급하지 않습니다. inverse predicate는 versioned ontology/DomainPack에 등록된 exact mapping이 있을 때만 사용합니다. LLM이 임의로 inverse 관계를 발명할 수 없습니다.

### 결정 G — ranking과 deduplication 순서를 고정합니다

각 lane은 다음 순서로만 처리합니다.

1. backend response schema 및 receipt 검증
2. QueryPlan, corpus snapshot과 index version binding 검증
3. `canonical_source_key` 생성
4. channel 내부 exact duplicate 병합
5. 각 channel을 `raw_rank`, 이후 `canonical_source_key` 오름차순으로 안정 정렬
6. 여러 channel이 같은 lane에 기여하면 RRF 적용
7. transparent ranking feature 계산
8. policy의 `max_candidates` cutoff 적용
9. 최종 동점은 `candidate_id` 오름차순으로 해결
10. 제외·중복·cutoff 개수를 lane result에 기록

RRF는 다음으로 고정합니다.

```text
RRF(d) = sum(1 / (60 + rank_channel(d)))
```

- 고정 상수: `k=60`
- raw score를 서로 직접 비교하거나 min-max로 조작하지 않음
- learned reranker는 O02-0002 범위에서 사용하지 않음
- future learned reranker는 별도 HumanDecision, version, qualification과 replay contract 필요
- RRF와 feature는 검색 우선순위이며 과학적 지지 강도가 아님

중복 identity는 다음 tuple로 고정합니다.

```text
canonical_source_key
+ source_version
+ source_snapshot_hash
+ source_locator
```

같은 lane 안에서는 위 identity가 같은 hit를 하나로 병합하고 모든 channel observation을 보존합니다. 서로 다른 evidence role/lane 사이의 dependency deduplication은 O03 책임이므로 O02가 임의로 없애지 않습니다.

### 결정 H — snapshot과 integrity 규칙을 고정합니다

다음 값은 하나의 lane execution 동안 변할 수 없습니다.

- `plan_hash`
- `corpus_snapshot_hash`
- `index_versions`
- backend/adapter version
- policy bundle hash
- cutoff policy

시작과 종료 사이 root snapshot 또는 index version이 달라지면 부분 결과를 성공으로 봉인하지 않고 다음으로 종료합니다.

```text
search_state: FAILED
stop_reason: integrity_failure
error_code: STALE_RETRIEVAL_SNAPSHOT
```

backend response의 declared snapshot이 request와 다르거나 candidate hash가 재계산과 다르면 동일하게 `FAILED`입니다.

### 결정 I — 실패, partial과 fallback 의미를 고정합니다

O01의 상태를 그대로 사용합니다.

| 상황 | lane state | stop reason |
|---|---|---|
| policy가 실행을 금지 | `BLOCKED` | `policy_blocked` |
| credential 없음 | `BLOCKED` | `credential_unavailable` |
| required backend 없음 | `BLOCKED` | `backend_unavailable` |
| provider가 오류 응답 | `FAILED` | `provider_failure` |
| malformed/unknown response | `FAILED` | `invalid_response` |

- malformed hit만 버리고 전체 성공으로 표시
- PARTIAL을 benchmark PASS에 포함
- backend error를 `SEARCHED_NONE`으로 표시

### 결정 J — “vector-only가 아님”을 실행 규칙으로 만듭니다

1. E1 이상에서는 O01의 class floor에 따라 `lexical`, `semantic`, `citation`, `temporal` lane이 실제로 선택돼야 합니다.
2. 필수 non-vector lane을 호출하지 않고 semantic 결과만 만든 run은 PASS할 수 없습니다.
3. 유효 후보가 한 개 이상 downstream으로 release될 때는 release set에 `LEXICAL`, `CITATION_GRAPH`, `RELATION_GRAPH` 또는 `EXTERNAL_INDEX` origin을 가진 후보가 최소 1개 있어야 합니다.
4. vector-origin 후보만 존재하면 후보 자체는 보존하지만 `multi_channel_verified=false`로 기록하고 retrieval run ceiling은 `PARTIAL`입니다.
5. 모든 필수 lane을 완전히 실행했지만 모든 lane이 `SEARCHED_NONE`인 경우는 bounded searched-none 결과로 PASS할 수 있습니다.
6. channel provenance가 없거나 조작된 후보는 `INVALID_RESPONSE`가 아니라 무결성 failure로 처리합니다.

4. Relation direction

closed enum:

- SAME_DIRECTION
- REVERSE_DIRECTION
- INVERSE_PREDICATE
- BIDIRECTIONAL
- NO_DIRECTION
- UNRESOLVED

SAME_DIRECTION은 canonical subject/predicate/object와 같은 방향이다.
REVERSE_DIRECTION은 같은 predicate에서 subject/object가 뒤집힌 경우다.
INVERSE_PREDICATE는 versioned ontology/DomainPack에 등록된 inverse
predicate와 뒤집힌 arguments가 같은 canonical fact를 표현한 경우다.
BIDIRECTIONAL은 양 방향을 명시적으로 주장한 경우다.
NO_DIRECTION은 symmetric/non-directional relation이다.
UNRESOLVED는 trustworthy mapping 또는 grounding이 부족한 경우다.

NO_DIRECTION과 UNRESOLVED를 direction match로 처리하지 않는다.
LLM이 inverse predicate를 임의 생성할 수 없다.

canonical relation A parent_of B의 exact fixtures:

- A parent_of B -> SAME_DIRECTION
- B parent_of A -> REVERSE_DIRECTION
- B child_of A -> INVERSE_PREDICATE
- both directions -> BIDIRECTIONAL
- A correlated_with B -> NO_DIRECTION
- ungrounded predicate/arguments -> UNRESOLVED

5. Ranking, deduplication and cutoff

처리 순서:

1. backend response/receipt validation
2. QueryPlan, corpus snapshot, index binding validation
3. canonical_source_key generation
4. exact duplicate collapse within channel
5. stable per-channel rank normalization
6. RRF fusion when multiple channels feed the same lane
7. transparent feature calculation
8. max_candidates cutoff
9. candidate_id ascending tie-break
10. excluded/duplicate/cutoff count recording

RRF formula:

RRF(d) = sum(1 / (60 + rank_channel(d)))

k=60으로 고정한다.
raw score를 channel 사이에서 직접 비교하지 않는다.
learned reranker는 O02-0002에서 사용하지 않는다.
retrieval rank/score를 scientific evidence strength로 해석하지 않는다.

duplicate identity:

canonical_source_key
+ source_version
+ source_snapshot_hash
+ source_locator

same-lane duplicate는 병합하되 모든 channel observation과 duplicate lineage를
보존한다. cross-lane dependency deduplication은 O03가 소유한다.

7. Failure, partial and fallback

- policy denial -> BLOCKED / policy_blocked

- required backend unavailable -> BLOCKED / backend_unavailable
- provider error -> FAILED / provider_failure
- malformed or unknown response -> FAILED / invalid_response

- valid partial set after budget exhaustion -> PARTIAL / budget_exhausted
- valid partial set after timeout -> PARTIAL / time_exhausted
- approved manual stop -> PARTIAL / manual_stop
- complete execution and zero candidates -> SEARCHED_NONE
- complete execution and candidates -> SEARCHED_WITH_RESULTS

silent cross-channel fallback은 금지한다.
backend error를 SEARCHED_NONE으로 기록하지 않는다.
planned backend/query family 중 하나라도 미완료면 complete state를 쓰지 않는다.
PARTIAL/BLOCKED/FAILED run을 benchmark success 표본에 포함하지 않는다.
